# Browser model feasibility — 2026-09-25

**Current evidence:** Exact OpenCV Zoo SFace ONNX runs in ONNX Runtime Web WASM and closely matches native OpenCV features on two development crops. Standard TensorFlow.js conversions of SFace and the exact-architecture GhostFaceNet float32 clone also passed synthetic output and input-gradient diagnostics in desktop Chrome. Their complete photo optimization, combined memory use and actual phone performance remain unverified. No research method has passed the protection requirements, so the public processor remains unavailable.

## Exact SFace forward inference route

### YuNet detection and alignment probe

The [OpenCV 4.13.0 YuNet implementation](https://github.com/opencv/opencv/blob/4.13.0/modules/objdetect/src/face_detect.cpp) accepts an 8-bit BGR image, pads right/bottom to multiples of 32, and builds a float32 NCHW BGR blob with default `blobFromImage` settings. Its 12 output tensors cover strides 8/16/32; it clamps class/object scores, takes their geometric mean, decodes XYWH and five landmarks, then applies NMS at score threshold 0.9, NMS threshold 0.3 and topK 5000. NMS uses integer-truncated boxes. The [SFace alignment implementation](https://github.com/opencv/opencv/blob/4.13.0/modules/objdetect/src/face_recognize.cpp) fits the five landmarks to its fixed template via a similarity transform and performs a 112×112 `INTER_LINEAR` warp.

The [native preparation script](browser/prepare_yunet_parity.py) reproduces the project's max-side-640 detector frame (`INTER_AREA` resize) from the same two development identities. Both 1350×1350 source images become 640×640 BGR detector frames. It saves the exact padded native blob, lossless decoded source PNG, native aligned PNG, detection in frame and original coordinates, raw SFace feature, OpenCV version, and SHA-256 values outside Git in `C:/Users/JordanStevenson/Downloads/FCKFACE-data/ort-browser/assets/yunet-manifest.json`. The source images and models remain local.

[ONNX Runtime Web WASM in Node](browser/yunet_node_parity.mjs) plus the [OpenCV postprocess translation](browser/decode_yunet.mjs) returned exactly one detection on each case. Across all 15 frame fields (XYWH, five landmarks and score), the maximum absolute differences from native `FaceDetectorYN` were **0.0000467** and **0.0000177**. This verifies numerical detection parity on shared native blobs, not browser image decoding/resizing. The [browser worker probe](browser/yunet_worker.mjs) uses the same hashed blob, maps landmarks to original coordinates, tests Canvas affine alignment against native 112×112 crop pixels, then feeds the Canvas crop to SFace and measures raw feature drift. [Local page](browser/yunet_parity.html) supports restart/cancellation by terminating the worker. The pixel and embedding results must be assessed before calling alignment faithful.

## Why this model

The prior optimizer used SFace, GhostFaceNet, ArcFace, and FaceNet512. The cached GhostFaceNet H5 is the smallest of those with an original-author release and a TensorFlow/Keras graph: **17,271,840 bytes** (16.47 MiB), SHA-256 `e4182ca2470dac3eb79974f4d5d54f2abdf66d7e231c6f3df4059a90bded1271`. The H5 contains **4,088,812 float32 values** (16,355,248 raw bytes), 298 layers, a 112×112×3 input and a 512-value embedding. Its serialized classes are Input, Conv2D, DepthwiseConv2D, BatchNormalization, PReLU, Activation, Add, Multiply, Concatenate, Reshape, Flatten and GlobalAveragePooling2D. TensorFlow.js Layers has these layer families and [its activation source includes hard sigmoid](https://github.com/tensorflow/tfjs/blob/master/tfjs-layers/src/activations.ts); no custom layer class appears in the H5. This makes it a plausible direct Keras-to-Layers conversion, **not proof that this particular file converts or that every browser backend differentiates it**. TensorFlow.js documents Keras H5 conversion to `model.json` plus weight shards and `tf.loadLayersModel`; its converter rejects unsupported operations. [Author release](https://github.com/HamadYA/GhostFaceNets/releases/tag/v1.2), [TF.js conversion guide](https://www.tensorflow.org/js/guide/conversion), [TF.js Layers API](https://js.tensorflow.org/api/latest/).

The author evaluates aligned **RGB 112×112 uint8** crops with `(pixel - 127.5) / 128`, followed by unit normalization of embeddings. Its five-landmark similarity alignment uses the published template and a skimage warp that converts back to uint8. A browser implementation must prove pixel parity for this crop path separately; the current UI's manual rectangle is not equivalent to five-landmark alignment. [Author evaluation](https://github.com/HamadYA/GhostFaceNets/blob/main/eval_folder.py), [author alignment](https://github.com/HamadYA/GhostFaceNets/blob/main/face_detector.py). The old local YuNet/SCRFD substitutions are development evidence, not author-pipeline parity.

OpenFace (14.6 MiB) and DeepID (1.54 MiB) appear in the old cache, but they were distributed through DeepFace for its earlier held-out audit, not located as original-author checkpoints with cleared artifact terms. The older notes identify GPL-3.0 source for DeepID and do not find a separate weight license for OpenFace. SFace is larger (38.7 MB) and has a clearer Apache-2.0 model-directory notice. Its ONNX form now has the forward-inference route above; its route to a differentiable TF.js Layers model has not been established here. ArcFace and FaceNet512 are much larger. See the old project's `MODEL-SOURCES.md` and `holdout-sources.md` for provenance; none of these previously used models may count as a new independent recognizer for FCKFACE's final gate.

## Conversion and parity blocker found

The cached author H5 stores a legacy `mixed_float16` policy on 296 layers. Current Keras 3 `load_model` in the old environment fails on that policy (`AttributeError: 'str' object has no attribute 'quantization_mode'`). Setting `TF_USE_LEGACY_KERAS=1` before TensorFlow import loads the H5 without changing the environment. DeepFace's reconstructed GhostFaceNet loads the same weights, but its layer defaults differ from the author graph (for example, early BatchNorm epsilon `0.001` versus author H5 `0.00001`). It is **not a parity baseline**: on one deterministic synthetic RGB crop its embedding differs from the author H5 by maximum absolute **0.218864**. An exact-architecture float32 clone differs by **0.052941** with cosine **0.999859**, reflecting at least the author graph's mixed precision; this single tensor is only a diagnostic.

Run the read-only [reference probe](browser/ghost_reference.py) with the prior environment's Python and its cached H5 path. It uses no personal image and prints artifact hash, synthetic-input embeddings, and the differences above. Do not convert the DeepFace reconstruction as if it were the author model.

An isolated scratch virtual environment reused the prior TensorFlow packages read-only. Installing the official [PyPI `tensorflowjs` 4.22.0 wheel](https://pypi.org/project/tensorflowjs/4.22.0/) with `--no-deps` downloaded 89 kB, but importing the converter failed immediately with `ModuleNotFoundError: No module named 'tensorflow_decision_forests'`. Its `tf_saved_model_conversion_v2.py` imports that package unconditionally, including for the requested Keras route. [TensorFlow Decision Forests states that it is available on Linux and macOS, with Windows users directed to WSL](https://pypi.org/project/tensorflow-decision-forests/). A read-only inspection of the official 4.13.0 wheel showed the same unconditional import. This initial Windows attempt did not reach conversion or browser inference. A later standard WSL attempt and supported dependency fix are recorded below.

The later isolated Ubuntu WSL environment used the official TensorFlow.js 4.22.0 converter with TensorFlow/tf-keras 2.19.0 and TensorFlow Decision Forests 1.12.0. Its first resolved dependency set failed before model loading: YDF 0.16 generated protobuf code required version 6 while TensorFlow used protobuf 5. The supported retry pinned YDF 0.11.0 (its metadata requires protobuf 5.29.1 through 5.x) and setuptools 81.0.0 for TensorFlow Hub compatibility. The documented `tensorflowjs_converter --input_format=keras` command then converted the exact author H5 to a Layers model with 298 layers and four weight shards, about 16.36 MB of weights. No converter code was patched. Assets remain outside Git. Conversion succeeded. Subsequent Chrome worker measurements passed synthetic forward and input-gradient diagnostics using a separately identified float32 inference clone; see below. The author conversion failed browser loading on a serialized L2 regularizer. A standard Keras float32 clone with the same weights and BatchNorm settings, with only training regularizers removed, loaded successfully. Native Linux and Windows author-H5 synthetic outputs differed slightly (cosine 0.999938), so conversion success alone is not numerical parity.

Compare Python and browser on the *same already-aligned RGB uint8 tensor* first: raw 512-vector, unit-vector cosine, and scalar-loss input gradient against Python `GradientTape` plus finite differences. Record maximum absolute error, cosine, gradient agreement, backend and memory. Treat any tolerance as a diagnostic chosen before looking at results; inspect discrepancies by layer. Then compare alignment outputs on permitted development images, and only then a full export path. No test here used AdaFace, MagFace, EdgeFace or TransFace.

TensorFlow.js exposes `tf.grad` and the Layers model format supports training/backpropagation. That does **not** establish this model's input gradient on every browser backend. The official WASM backend explicitly says it still lacks some gradient operations, so a WASM inference pass cannot stand in for a gradient pass. Test CPU and WebGL in an actual worker on desktop, iPhone Safari and Android Chrome; verify gradients, cancellation and peak memory before selecting a backend. [TF.js gradient API](https://js.tensorflow.org/api/latest/), [Layers converter README](https://github.com/tensorflow/tfjs/blob/master/tfjs-converter/README.md), [WASM backend limits](https://github.com/tensorflow/tfjs/blob/master/tfjs-backend-wasm/README.md), [official worker example](https://www.tensorflow.org/js/tutorials/training/web_worker).

## Measured GhostFaceNet browser gradients

The [reproducible conversion and worker probes](browser/ghost_tfjs_conversion.md) passed their predeclared synthetic numerical checks in desktop Chrome on CPU and WebGL. The float32 clone's browser raw maximum error was about 1.1×10⁻⁵; gradient cosine versus the frozen Python float32 reference exceeded 0.9999999, and all three finite-difference coordinates passed. This checks one deterministic aligned tensor, not a complete photo optimizer.

CPU input gradients took about 19 seconds. WebGL's first gradient took about 45 seconds; three later gradients took 195–246 ms and forwards 39–73 ms. Model/input/target disposal reduced tensor count and occupied GPU bytes to zero, while the approximately 345 MB allocated texture pool remained free for reuse. These counters exclude total browser process memory. Root also cancelled an active worker, restarted it and observed a complete numerical pass, then terminated it.

The current acceptance preference permits approximately 90 seconds with a visible progress bar (REQUIREMENTS.md). Cold loading and compilation must be included in that workflow measurement. These separate synthetic probes are not a measured two-model photo workflow.

## Measured SFace browser gradients

The [standard SFace conversion and probe](browser/sface_tfjs_conversion.md) used a verified private copy of the original ONNX, the supported onnx2tf TensorFlow-converter backend and the unmodified TensorFlow.js converter. The resulting 38.63 MB GraphModel takes NHWC RGB values in 0–255; its own graph contains normalization. Native synthetic output and gradient parity passed before browser testing. The record also preserves a failed exporter, an accidental archive modification that was restored and a local HTTP loading stall corrected with the supported streaming loader. No modified model bytes replaced the calibrated reference.

Desktop Chrome CPU and WebGL passed all five predeclared numerical checks, including three coordinate finite differences. Raw maximum errors versus native OpenCV were 2.03×10⁻⁶ and 5.07×10⁻⁶; input-gradient cosines exceeded 0.99999997. CPU forward/gradient took about 5.88/58.22 seconds during concurrent native research. WebGL's first forward/gradient took 3.29/8.64 seconds. In a subsequent worker, three warm forwards took 42.1–42.8 ms and gradients 155.7–158.9 ms, with unchanged numerical results.

After model/input/target disposal, both backends reported zero tensors and occupied bytes. WebGL retained about 560 MB of free allocated texture cache. These counters exclude browser process memory and do not establish a peak or combined two-model memory bound. Root cancelled an active CPU gradient, restarted a fresh WebGL worker, observed a full numerical pass and stopped it. The numerical observations are transcribed from the rendered probe report and kept outside Git. No complete photo optimizer or actual iPhone/Android test has passed yet.

## Size, rights and integration boundary

The float32 weights alone need **16.36 MB**; the sum of one output tensor per layer for a 112×112 batch of one is about **68.5 MB** if all retained. Gradient tape, temporary tensors, WebGL textures and a decoded full photo add memory, so no one-minute or mobile-memory claim follows from the checkpoint size. Keep model work on an aligned face crop, track `tf.memory()` and browser process memory during a short gradient probe, and dispose tensors/worker between jobs. These are estimates, not a benchmark.

The author's repository has an [MIT license for its code](https://github.com/HamadYA/GhostFaceNets/blob/main/LICENSE), and the checkpoint is provided on its release page. Neither that fact nor DeepFace's MIT wrapper establishes separate rights for the pretrained artifact or its MS1MV3 training data. Confirm redistribution and commercial-use terms before adding converted weights to a public bundle. Keep the cached H5 and all derived weights out of Git until that is resolved. The current unvalidated dot preview remains a visual study; this model conversion would supply an optimization component only, not facial privacy evidence.
