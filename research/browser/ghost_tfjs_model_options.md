# Second differentiable browser recognizer: read-only feasibility (2026-09-25)

The converted GhostFaceNet float32 inference clone passed a synthetic TensorFlow.js input-gradient probe. It is still only **one development recognizer**. A second browser gradient must be independently demonstrated before treating a browser optimization loop as cross-model. This note records a possible standard route for the existing SFace ONNX and the public artifact-rights boundary; it does not run a conversion, inspect a personal photo, or select a release model.

## SFace ONNX → TF.js

The cached OpenCV Zoo `face_recognition_sface_2021dec.onnx` is 38,696,353 bytes, SHA-256 `0ba9fbfa01b5270c96627c4ef784da859931e02f04419c829e83484087c34e79`. Read-only inspection with the existing `onnx` package found ONNX opset 11, **88 nodes**, one actual runtime input `data` of shape `[1,3,112,112]`, one output `fc1` of shape `[1,128]`, and 174 initializers that also appear as graph inputs. Operator counts: BatchNormalization 29, Conv 27, PRelu 27, Sub 1, Mul 1, Dropout 1, Flatten 1, Gemm 1. There are no custom-domain nodes. The Sub/Mul nodes implement the ONNX graph's input scaling; the browser caller must still supply native OpenCV's RGB NCHW float32 pixels in 0–255 after its five-landmark alignment, rather than adding another normalization. [OpenCV Zoo's SFace model notes](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/README.md) describe its model family and conversion provenance.

The maintained [`onnx2tf` project](https://github.com/PINTO0309/onnx2tf) documents all eight SFace node families as supported and has an explicit [ONNX → SavedModel → standard TF.js GraphModel recipe](https://raw.githubusercontent.com/PINTO0309/onnx2tf/main/README.md) (section 19): `onnx2tf -i model.onnx -fdosm -osd`, then `tensorflowjs_converter --input_format tf_saved_model --output_format tfjs_graph_model saved_model tfjs_model`. Current onnx2tf defaults to its `flatbuffer_direct` path and says `-fdosm` emits a float32 SavedModel from its intermediate representation. It also offers an H5 export (`-oh5`) that might allow the TF.js Layers route, but its generated layer serialization for this model has **not** been inspected. None of these conversion paths has been run on SFace here.

This is a **forward-conversion prospect, not a confirmed differentiable model**. The [official TF.js converter](https://github.com/tensorflow/tfjs/blob/master/tfjs-converter/README.md) converts SavedModel to GraphModel, loaded with `tf.loadGraphModel`; it does not promise that every converted graph executes within `tf.grad` on CPU/WebGL. The documented onnx2tf path may produce unsupported TF.js ops or a graph without usable input gradients. The single SFace Dropout node must be verified as inference-disabled after conversion, and the NCHW/NHWC interface and output must be compared to exact native OpenCV on the same synthetic aligned tensor before a gradient comparison. If standard conversion succeeds, independently test scalar cosine-loss input gradient against a TensorFlow or finite-difference reference, then browser CPU/WebGL worker parity and actual crop alignment. A failed conversion or nonfinite/incorrect gradient ends that route; do not substitute an unverified custom graph or claim second-model support from ONNX Runtime Web inference alone.

The [SFace directory](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/README.md) **affirmatively declares Apache-2.0 for all its files**, including the ONNX file in that directory. Its exact training dataset is not documented there. [OpenCV Zoo issue 313](https://github.com/opencv/opencv_zoo/issues/313) asks for further provenance clarification, but the unanswered third-party issue does not revoke or override the directory's license declaration. This is separate from the technical conversion test and from GhostFaceNet's checkpoint terms; no public model bundle is needed for the current unvalidated method.

## GhostFaceNet checkpoint terms

The [author's repository](https://github.com/HamadYA/GhostFaceNets) has an [MIT `LICENSE`](https://github.com/HamadYA/GhostFaceNets/blob/main/LICENSE) for its software and offers the cached GhostFaceNetV1 1.3/S1 ArcFace checkpoint through its [v1.2 release](https://github.com/HamadYA/GhostFaceNets/releases/tag/v1.2). The author [README](https://github.com/HamadYA/GhostFaceNets/blob/main/README.md) identifies that model as trained on **MS1MV3** and links to InsightFace's MS1M-RetinaFace dataset. I found no distinct checkpoint license or express public browser redistribution/commercial-use grant in those author pages; a GitHub release download and repository code license alone do not settle that scope. [InsightFace's own license statement](https://github.com/deepinsight/insightface#license) says its training data and models trained with that data are available for noncommercial research, while code is MIT. That statement is relevant to the training-data provenance but does not itself resolve the exact author checkpoint's terms. The derived TF.js shards contain the same weights byte-for-byte, so conversion does not avoid the rights question. Keep the H5 and converted shards local; public bundling needs an affirmative artifact/training-data rights basis.
