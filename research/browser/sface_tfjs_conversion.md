# SFace standard TensorFlow.js conversion attempt (2026-09-25)

This is a synthetic-only **development-model** conversion and Chrome feasibility check. No photographs, final-panel models, or public assets were involved. Outputs and logs are outside Git at `C:/Users/JordanStevenson/Downloads/FCKFACE-data/runs/sface-tfjs-conversion-v1/`. The original OpenCV Zoo SFace ONNX is 38,696,353 bytes, SHA-256 `0ba9fbfa01b5270c96627c4ef784da859931e02f04419c829e83484087c34e79`.

The current [official onnx2tf 2.6.9 package](https://pypi.org/project/onnx2tf/2.6.9/) requires Python 3.12 and pins TensorFlow 2.21.0, protobuf 7.35.1, and its other dependencies. A separate task-owned Ubuntu WSL venv at `/home/jordan/fckface-sface-converter-v1/venv` installed `onnx2tf[tensorflow]==2.6.9`; `pip check` passed. The earlier GhostFaceNet TensorFlow.js converter venv was left unchanged. The exact resolved package versions and install log are in the external run directory.

The [maintainer's standard ONNX→SavedModel→TF.js recipe](https://raw.githubusercontent.com/PINTO0309/onnx2tf/main/README.md) was first attempted with `-tb flatbuffer_direct -fdosm -osd`; its exact command and output are frozen in `onnx2tf.log` and the external run record.

The first, direct-exporter attempt used a WSL symlink pointing into the archive. The ONNX has opset 11, 88 nodes and one actual runtime input `data` `[1,3,112,112]`; the remaining 174 declared graph inputs are initializers. The direct converter emitted an intermediate 38.55 MB float32 TFLite file, then **failed at SavedModel export**. Its `_kernel_depthwise_conv2d` passes a four-element `dilations` list to `tf.nn.depthwise_conv2d`; pinned TensorFlow 2.21 reports `ValueError: input.shape.rank must be at least 5. Received: input.shape=(1, 112, 112, 32) with rank 4`. The complete traceback is `onnx2tf.log`. This is a concrete failure in the standard exporter with its declared dependency set. No source patch or hand-coded network was used.

The existing read-only OpenCV/onnx2torch environment generated full seed-0 synthetic RGB112 native output, target, input gradient, and directional finite differences in `synthetic-reference.json` (outside Git) using [sface_tfjs_reference.py](sface_tfjs_reference.py). It reproduced the earlier frozen diagnostic's OpenCV-vs-onnx2torch raw maximum difference `2.3841858e-6` and directional derivative `4.5097833e-5`.

Read-only inspection of the same pinned 2.6.9 CLI/source found the documented alternative `-tb tf_converter -osd`, without `-fdosm`. Its first run succeeded but **normalized the input ONNX in place through the WSL symlink**, changing the authoritative archive at 17:38:33 UTC to 38,692,565 bytes / SHA-256 `827d2b58fe491fa70fe96d1b4998a07ac0c3e58a0e81033a0ffb713793c3a0e9`. This violated the archive preservation requirement. The changed bytes and log were preserved externally. The original was redownloaded from [OpenCV Zoo](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/face_recognition_sface_2021dec.onnx), hash-checked, and restored at 17:42:23 UTC. The unsafe symlink was removed without touching its target. Any evidence loading the archive during that interval is invalid. The failed direct-exporter log predates this mutation.

The changed ONNX removed 174 initializer graph inputs, added 87 value-info entries, and reserialized all 174 initializer tensors from `float_data` to `raw_data`. All 88 node protos were byte-equal; all initializer tensors had identical decoded numerical bytes, although their serialized protos differed. The exact comparison is preserved in external `model-diff.py`. Neither this numerical equivalence nor the successful first output excuses the accidental archive write; the first output was discarded as conversion evidence.

A verified original was copied into the task-owned **regular file** `/home/jordan/fckface-sface-converter-v1/sface-private-original.onnx`. The supported `-tb tf_converter -osd` route was rerun against that copy, producing a fresh `onnx2tf-tf-converter-private/` SavedModel. The converter normalized only the private copy; the archive still hashes to the original after conversion. Native synthetic forward and input-gradient parity passed all predeclared limits: raw maximum difference from OpenCV `2.5928e-6` (limit `1e-3`), raw cosine `0.999999999997` (limit `.99999`), input-gradient cosine vs frozen onnx2torch `0.9999999999996` (limit `.99`), exact repeat, and three of three finite differences. `native-parity-private.json` records all numbers. A separate cosine-loss reference and converted SavedModel parity check also passed with input-gradient cosine `0.9999999999996` and three of three coordinate checks (`synthetic-cosine-reference.json`, `native-cosine-parity.json`).

The unmodified standard TensorFlow.js 4.22.0 converter subsequently produced `tfjs-graph-private/`: a `graph-model` with 11 files / 38,628,903 bytes, input `data:0` float32 `[1,112,112,3]`, output `Identity:0` `[1,128]`, and `model.json` SHA-256 `482fe784b7b4847397459ecf5a0698dfda0bca569815d4a0fc687dd925937fbc`. The conversion log is `tfjs-converter-private.log`.

The first Chrome CPU probe remained in model loading after only six of ten weight shards were requested; the root task cancelled it at 18:00:41 UTC. The worker and observation were frozen externally. TF.js 4.22's documented `LoadOptions.streamWeights` then let all ten shards load; the next probe stopped before inference because GraphModel's JavaScript API exposes the names as `data` and `Identity`, stripping the `:0` suffixes in the artifact signature. That error and worker were also frozen. The current worker uses the API names and preserves the same graph, weights, synthetic input, and numerical limits. These were loading/probe integration fixes, not model conversion or threshold changes.

The corrected Chrome **CPU** synthetic probe passed at 18:06 UTC: raw maximum difference from OpenCV `2.0266e-6` (limit `1e-3`), unit cosine `0.999999999997` (limit `.99999`), cosine-loss input-gradient cosine `0.9999999738` (limit `.99`), finite nonzero gradient, and three of three preset finite-difference coordinates. It reported 434.9 ms model load, 5.88 s forward and 58.22 s gradient; those timings overlapped another native scoring job and should not be treated as an isolated browser performance estimate. After disposal, `tf.memory()` reported zero tensors, buffers, and occupied bytes, but it does not measure total browser/process memory.

Chrome **WebGL** also passed at 18:08 UTC with raw maximum difference `5.0664e-6`, unit cosine `0.999999999991`, gradient cosine `0.999999999999`, and finite differences three of three. It loaded the model in 407.9 ms and took 3.29 s for first forward and 8.64 s for first gradient. A new worker's subsequent three warm forwards took 42.1/42.7/42.8 ms; gradients took 158.9/157.7/155.7 ms. Every warm run retained the same numerical pass. These are browser-worker synthetic times on this desktop, not a complete photo optimizer or phone measurement. After disposal, `tf.memory()` reported zero tensors, buffers, and occupied GPU bytes; its 560,383,188-byte allocated WebGL texture cache remained reported as free. Total browser/process memory was not measured.

Cancellation was visibly tested: a CPU worker started at 18:09:45 UTC, was seen computing its gradient at 18:10:06, and showed Stopped after cancellation at 18:10:10. A fresh WebGL worker restarted at 18:10:12 and passed the same raw, gradient, and three coordinate checks at 18:11:23; it was stopped at 18:12:45. This checks worker isolation and restart on the synthetic probe, not complete product cancellation.
